## 接続関連の問題

### 問題: PS5からのテレメトリが受信できない

**症状:**
- Dockerコンテナは起動しているが、PS5との接続が確立されない
- ログに `Heartbeat sent to ...` は出るが `Started receiving data:` が出ない
- または `Decryption failed` が大量に出続ける

**原因:**
- PS5のIPアドレスが間違っている
- PS5とPCが同じネットワークに接続されていない
- PS5のテレメトリ送信がOFFになっている
- ファイアウォールでUDPポートがブロックされている
- 復号の失敗（`Decryption failed`）が続く場合、`decoder.py` の Salsa20 import 状態を疑う

**解決方法:**

1. **PS5のIPアドレスを確認**
   - PS5で「設定」→「ネットワーク」→「接続状態」→「接続状態の詳細」→「IP アドレス」
   - メモしたIPアドレスと `config.json`（または環境変数 `PS5_IP`）の `ps5_ip` が一致しているか確認

2. **ネットワーク接続を確認**
   ```bash
   # PCからPS5にpingを送信
   ping <PS5のIPアドレス>
   ```
   - pingが通らない場合、ネットワーク設定を確認

3. **GT7のテレメトリ設定を確認**
   - GT7で「オプション」→「設定」→「コントローラー設定」→「通信設定」
   - 「テレメトリデータ送信」がONになっているか確認

4. **ファイアウォール設定を確認**
   - UDPポート 33740（受信）がブロックされていないか確認
   - Windows: ファイアウォールの受信の規則を追加
   - Linux（本番 abem2 は ufw）: `sudo ufw allow from <PS5のIP> to any port 33740 proto udp`。コンテナは `network_mode: host` なので Docker の自動開放は効かず、ufw のルールがそのまま当たります。遮断されていれば `journalctl -k | grep "UFW BLOCK" | grep DPT=33740` に PS5 からのパケットが並びます
   - **実績（#639、2026-10-16）**: 別作業で ufw を有効にした 2026-10-09 以降、PS5 からの UDP が 1 週間遮断されて記録が止まっていた。ログは `Heartbeat sent` だけが続き、エラーは出ない（受信できないだけ）ので気づきにくい
   - macOS: システム環境設定→セキュリティとプライバシー→ファイアウォール

5. **サーバーログで受信状況を確認**
   ```bash
   docker compose logs -f
   ```
   - 正常時は `Heartbeat sent to ...` → `Started receiving data: 344 bytes from (...)` → `Parsed: XX.X km/h, RPM: XXXX, Gear: X` → `Telemetry stream active` の順に流れる
   - `Decryption failed` が継続する場合は、`decoder.py` の `_try_decrypt` 内で `from Crypto.Cipher import Salsa20` が遅延 import されているか確認（過去に import 漏れで5日間機能不全になった実績あり）

### 問題: 別の PC からダッシュボードが開けない（接続できない・タイムアウト）

**症状:**
- サーバーの PC 自身では `https://localhost:8080` が開くのに、LAN の別 PC から `https://abem02.local:8080/` や IP 指定で開けない（「接続できません」「応答時間が長すぎます」）
- サーバーのログに、その PC からの `GET /` が出ない

**原因:**
- サーバー側のファイアウォール（ufw）が TCP 8080 を遮断している。コンテナは `network_mode: host` なので、Docker を使っていても ufw のルールが必要（#639）
- `.local` 名が解決できない（mDNS）。この場合は IP 指定なら開く

**解決方法:**
1. サーバーで遮断の記録を確認: `journalctl -k | grep "UFW BLOCK" | grep DPT=8080`
2. LAN からの 8080/TCP を許可: `sudo ufw allow from 192.168.1.0/24 to any port 8080 proto tcp comment 'gt7 dashboard'`
3. 同時に PS5 からのテレメトリも開いているか確認: `sudo ufw status numbered` に 33740/udp の行があること（無ければ上の「PS5からのテレメトリが受信できない」の 4 を実施）
4. 証明書は `abem02.local` 名義（SAN に IP は無い）なので、IP 指定より `https://abem02.local:8080/` の方が警告が少ない

### 問題: ブラウザでダッシュボードが開けない（HTTPS警告）

**症状:**
- `https://localhost:8080` にアクセスすると「この接続ではプライバシーが保護されません」等の警告が出る

**原因:**
- 自己署名証明書を使用しているため（本仕様。本番運用でも自己署名）

**解決方法:**

1. **警告を続行**
   - Chrome: 「詳細設定」→「localhost にアクセスする（安全ではありません）」
   - Firefox: 「詳細」→「危険性を承知で続行」
   - Edge: 「詳細」→「localhost に進む（安全ではありません）」

2. **証明書を再生成したい場合**
   - ホストの `ssl/` ディレクトリ内の `server-cert.pem` / `server-key.pem` を差し替える（`docker-compose.yml` が `./ssl` を読み取り専用でマウントするので、再ビルドは不要。コンテナの再起動で反映。#596）
   - `ssl/` が無い（または `config.json` の `ssl_cert` / `ssl_key` の先にファイルが無い）ときは、起動ログに `SSL cert/key not found ... falling back to HTTP` と出て平文 HTTP で起動します（`http://localhost:8080`。音声コマンドは https でしか動きません）

## データ表示関連の問題

### 問題: ダッシュボードは表示されるがデータが更新されない

**症状:**
- ダッシュボードにはアクセスできる
- 速度やRPMなどが0のままで変化しない

**原因:**
- GT7が起動していない
- レース画面が表示されていない
- WebSocket接続が確立されていない

**解決方法:**

1. **GT7を起動してレース画面を表示**
   - タイムアタックまたはレースモードで走行を開始
   - メニュー画面ではテレメトリが送信されません

2. **WebSocket接続を確認**
   - ブラウザでF12を押して開発者ツールを開く
   - Consoleタブで WebSocket 接続成功のログ（`INIT` / `WS` 系）が表示されているか確認
   - Networkタブで `/ws` 接続がステータス 101（Switching Protocols）になっているか確認

3. **サーバーログを確認**
   ```bash
   docker compose logs -f
   ```
   - `Started receiving data: ... bytes` と `Parsed: XX.X km/h` が表示されているか確認
   - 表示されない場合は接続関連の問題を参照

## グラフ表示関連の問題

### 問題: グラフが表示されない

**症状:**
- 速度やRPMなどの数値は表示される
- グラフ（チャート）が表示されない

**原因:**
- uPlotライブラリが読み込まれていない
- ブラウザキャッシュの問題
- JavaScriptエラーが発生している

**解決方法:**

1. **ブラウザを強制リロード**
   - Windows: `Ctrl + F5`
   - Mac: `Cmd + Shift + R`

2. **uPlotライブラリが読み込まれているか確認**
   - F12で開発者ツールを開く
   - Consoleタブで以下を入力:
     ```javascript
     typeof uPlot
     ```
   - `"function"` と表示されればOK
   - `"undefined"` と表示される場合、ライブラリが読み込まれていない

3. **JavaScriptエラーを確認**
   - Consoleタブに赤いエラーメッセージがないか確認
   - エラーがある場合、以下を確認:
     - `uplot.min.js` ファイルが存在するか
     - ファイルサイズが約51KBであるか

4. **ネットワークタブを確認**
   - F12 → Networkタブ
   - ページをリロード
   - `uplot.min.js` と `uplot.min.css` がステータス200で読み込まれているか確認

## パフォーマンス関連の問題

### 問題: 表示が遅い/カクつく

**症状:**
- グラフの更新が遅れる
- ブラウザが重くなる

**原因:**
- 複数のブラウザタブでダッシュボードを開いている
- PCのスペックが不足している
- ネットワーク遅延

**解決方法:**

1. **不要なブラウザタブを閉じる**
   - 複数タブでダッシュボードを開いていると、それぞれでWebSocket接続が作成されます

2. **PCのスペックを確認**
   - 推奨スペック: デュアルコア以上、4GB以上のメモリ

3. **データ更新頻度を調整**
   - 画面側の更新レート（UI 30fps / チャート 20fps / マップ 10fps）は `constants.js` の設定値で、ここを下げると描画の負荷が減ります（変更後は再ビルドが必要）
   - ANALYSIS で使わないカードは CARDS（表示グループ）で非表示にすると、その分の描画が止まります

## 環境設定関連の問題

### 問題: Dockerが起動しない

**症状:**
- `docker compose up` でエラーが発生する

**原因:**
- Dockerがインストールされていない
- Dockerデーモンが起動していない
- ポート8080が使用中

**解決方法:**

1. **Dockerがインストールされているか確認**
   ```bash
   docker --version
   docker compose version
   ```

2. **Dockerデーモンの状態を確認**
   ```bash
   docker ps
   ```
   - エラーが出る場合、Dockerアプリを起動

3. **ポート8080が使用中か確認**
   ```bash
   # Linux/Mac
   lsof -i :8080

   # Windows
   netstat -ano | findstr :8080
   ```
   - 使用中の場合、他のアプリを停止するか `config.json` で `http_port` を変更

## コース推定関連の問題

コース推定はバックエンドで算出され、WebSocketメッセージの `course` フィールドとして配信されます。REVIEW ビューの比較サマリと全カード再生の再生バータイトルにコース名として表示されるほか、フィールド自体はライブ表示でも取得可能です。

### 問題: コース名が「Unknown Track」と表示される

**症状:**
- WebSocketメッセージの `course.name` が正しく推定されない（`course.id` が `unknown` のまま）

**原因:**
- コースデータベースにそのコースの情報が登録されていない

**解決方法:**

1. **新しいコースを学習させる**

   ```bash
   PYTHONPATH=. python3 tests/test_course_detection.py --regenerate
   ```
   - 実行場所（ホスト側リポジトリルート）や `--output` オプション等の注意事項は [USER_GUIDE「新しいコースを学習させる」](USER_GUIDE.md#新しいコースを学習させる) を参照

2. **手動でコースを追加**
   - `course_database.json` を編集
   - 新しいコースの座標範囲を追加

## テストモード関連の問題

### 問題: TEST MODEが動作しない

**症状:**
- ツールバーの **● TEST MODE** をクリックしても反応しない
- デモデータが表示されない

> ※ TEST MODE トグルには誤操作防止の連打防止があります。詳細は [TEST MODE ガイド](test-mode.md)を参照してください。

**解決方法:**

1. **ブラウザコンソールでエラーを確認**
   - F12 → Consoleタブ
   - JavaScriptエラーがないか確認

> ※ TEST MODE は合成テレメトリパケットをブラウザ内で直接処理するため、WebSocket 接続（サーバー稼働）は必須ではありません。

### 問題: TEST MODE中にPS5の実走データが表示されない

**症状:**
- TEST MODE を実行したまま GT7 で走行しても、ダッシュボードにデモデータしか表示されない

**原因:**
- 仕様です。TEST MODE 実行中は、デモ（5Hz）とライブ（60Hz）が表示を奪い合わないよう、実走テレメトリのライブ描画が一時停止されます

**解決方法:**
- ツールバーの **● TEST MODE** をクリックして停止すると、ライブ描画が再開されます（デモのラップ・BEST・最高速・グリッド順位は停止時にリセットされ、実走データに残留しません）

## 表示モード関連の問題

### 問題: ANALYSIS / DRIVE / REVIEW ビューの切り替え方が分からない

**症状:**
- 全パネル表示（ANALYSIS）から、走行用の最小表示（DRIVE）や過去ラップのレビュー（REVIEW）に切り替えたい

**解決方法:**

1. **ヘッダーの操作ツールバーを使用**
   - ツールバー左端の **ANALYSIS│DRIVE│REVIEW** セグメントで、切り替えたい側をクリック（点灯している側が現在のビュー。点灯側のクリックは無効）
   - DRIVE / REVIEW 表示中もツールバーは残るため、**ANALYSIS** をクリックすれば1クリックで戻れる
   - 選択はブラウザの localStorage に保存され、リロード後も復元される

2. **各ビューの違い**
   - **DRIVE**: 走行中向け最小表示（ギア特大・シフトライト・ライブデルタ中心）。0.2秒で読める構成
   - **ANALYSIS**: 全パネル表示（チャート・3D姿勢・タイヤ詳細・距離解析・ラップ履歴等）
   - **REVIEW**: 記録済みの過去ラップの一覧・距離基準比較。全カード再生の起点にもなる

### 問題: DRIVE ビューの表示項目が一部見えない

**症状:**
- DRIVE ビューで一部パネルが表示されない

**原因:**
- DRIVE ビューは意図的に表示項目を絞っている（F1 ステアリングディスプレイ流の設計）

**解決方法:**
- 全項目を見たい場合は ANALYSIS ビューに切り替え（DRIVE の絞りは仕様です）

## REVIEW・記録関連の問題

### 問題: 一覧の周回に「⚠複数コース」が付く・ラップ推移やまとめに出てこない

**症状:**
- REVIEW の一覧で、ある周回に「⚠複数コース」の印が付く
- その周回が LAP TIME TREND・SESSION SUMMARY・過去ベスト基準のデルタ・予測の参照に使われない

**原因:**
- 2026-10-15 より前の記録では、セッションをやり直したり別のコースへ移ったりしても記録が区切られず、1 つのファイルに複数のコースのサンプルが混在することがありました（#617）。距離基準の比較ができないため、自動の解析から外しています

**解決方法:**
- 仕様です。A/B の選択・再生はできます。2026-10-15 以降の記録は、ラップ数の減少・60 秒超の中断・位置の瞬間移動で自動的に別ファイルに分かれるので、新しい記録には付きません
- どうしても使いたい場合は、`/api/laps/{file}` の `meta.courses` でコースごとのサンプル数を確認し、該当部分だけを別ファイルに切り出してください

### 問題: 再生が最初の数秒だけ速い・タイムデルタの冒頭がずれる

**原因:**
- 古い記録では、ラップ切替時の保存中に受信が止まり、その間のパケットがほぼ同じ時刻で記録されていました（#602）

**解決方法:**
- 2026-10-15 の更新以降、サーバーが読み出し時に本来の間隔で並べ直すので、古い記録でもそのまま直っています。まだ起きる場合はブラウザを Ctrl+F5 で再読み込みしてください

### 問題: 記録の途中でサーバーが落ちた

**解決方法:**
- `gt7data/.checkpoint_current_lap.jsonl` に、落ちる直前までの進行中ラップのサンプルが 5 秒ごとに追記されています（#621）。復旧手順は [development.md](development.md) の「進行中ラップのチェックポイント」を参照してください
- サーバーのログに `Recording split: reason=...` と出ていれば、それは異常ではなく、記録を意図して区切った記録です

## 予測関連の問題

### 問題: STRATEGY の PRED（ラップタイム予測）が `--` のまま

**原因:**
- 予測は、同じコース×車種の記録が十分にあり、検証誤差（MAE）が 3% 以下と確認できた組み合わせ（`models/gated_groups.json`）だけに出ます。それ以外は中立表示の `--` です
- コースが未推定（Unknown Track）の間は問い合わせません

**解決方法:**
- 同じコース×車種で周回を重ねて記録を増やし、次の再学習（毎週日曜 04:00、`scripts/retrain_cron_wrapper.py`）を待つか、手動で `python3 scripts/retrain_cron_wrapper.py` を実行します。結果は `scripts/logs/retrain_*.log` と `models/training_summary.json` で確認できます
- 学習済みの組は `models/gated_groups.json` のキー（`<course>__<car_id>`）で確認できます

### 問題: PRED の下の「学習 N 日前」が大きい・再学習の失敗の通知が来た

**原因:**
- 週次の再学習が動いていない（cron 未登録・docker に触れない・学習の失敗）

**解決方法:**
- `crontab -l` に `retrain_cron_wrapper.py` の行があるか確認（登録方法は [scripts/README.md](../scripts/README.md)）
- 8 日以上実行されていないと、`disk_guard.py`（4 時間ごと）が「週次ジョブが実行されていない」を通知します（#632）。この通知が来たら cron の行と cron 自体の稼働を確認します
- `scripts/logs/retrain_*.log` の先頭の `# exit=` と末尾のエラーを確認。通知の本文は `~/DISK_ALERT.txt` にも残ります
- 「品質ゲートを通る組が減った」の通知は失敗ではありません。新しい記録を加えた検証で誤差が 3% を超えた組が外れただけで、その組の予測が `--` に戻ります

## 記録の容量関連の問題

### 問題: ディスクの警告（85% / 90%）の通知が来た

**原因:**
- `scripts/disk_guard.py`（4 時間ごと）が「/」と `gt7data` の載るファイルシステムの使用率を見て通知しています。90% を超えると、`gt7data` の古い記録を `gt7data_trash/` へ退避します（物理削除はしません）

**解決方法:**
- `scripts/logs/disk_guard.log` で、どちらのファイルシステムが増えたかを確認します。`gt7data` 以外（別の作業のファイル移動など）が原因なら、ダッシュボードの設定は変えずにそちらを片付けます
- `gt7data` が原因なら、`config.json` の `data_retention`（`max_total_gb` / `max_age_days`）を見直して、`sudo python3 scripts/gt7data_rotate.py --apply` を実行します（dry-run で対象を先に確認できます）

### 問題: 「週次ジョブが実行されていない」の通知が来た

**原因:**
- 週次ローテーション（root の cron、日曜 03:00）または再学習（利用者の cron、日曜 04:00）のラッパーが最後に動いた目印（`scripts/logs/.rotate_last_run` / `.retrain_last_run`。無ければ `rotate_*.log` / `retrain_*.log` の名前の日付）が 8 日より古い。crontab の行の消失、cron の停止、ラッパーの起動失敗のどれか（#632）

**解決方法:**
- `crontab -l`（abem）と `sudo crontab -l`（root）に該当の行があるか確認します（行の内容は [scripts/README.md](../scripts/README.md)）
- 行があるのに動いていないなら、`systemctl status cron` と `scripts/logs/rotate_cron.log` の末尾を確認します
- ラッパー自体の失敗（python3 が無い等）は別の通知「gt7data rotate: ラッパー例外」「予測モデルの再学習: 失敗」として届きます（#631 / #626）

### 問題: 記録が消えた

**解決方法:**
- 週次ローテーション（日曜 03:00）の対象は `gt7data_trash/<日付>/` に 14 日間残っています。戻したいファイルを `gt7data/` へ移し、`gt7data/.rotate_keep` にファイル名を書くと、以後は保護されます
- 実行の記録は `scripts/logs/rotate_*.log` にあります
